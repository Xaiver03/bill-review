# 产品化方案（billkit）

> 状态：Planned · 最后核验：2026-11-20
> 方向：开源产品，面向同类极客（复式记账 / 数据洁癖 / 愿意在终端里跑管道的人）

## 0. 定位一句话

**billkit 是「个人账单的批量 ETL 台」**：把微信 / 支付宝 / 招行 / 工行导出的脏账单，批量化清洗、去重、分类、复核，再批量化导出到任意账本。它是一个**可在终端里脚本化的本地管道**，不是一本账。

关键约束：**"批量处理"是能力，不是定位。** 不把它当卖点，把它当交付方式——用户要的是"省下来的几小时 + 一份能直接用的干净账本"。

## 1. 与记账软件的关系：上游、且出口中立

账单软件（木木记账等）= 账簿端（记录、管理、看报表）。billkit = 它**上游的数据管道**。关系是"给账簿喂数据"，不是"替代账簿"。

- 不抢用户已有的记账习惯，不需要迁移；
- 天然互补：一次灌 6000 条脏账是账簿软件不解决的事；
- 分类结果是**中立资产**：能喂木木，也能喂 Firefly、beancount。

**决策：出口可插拔、进口才是护城河。** 拒绝把产品绑死在单一账簿上；真正的长期价值在"微信/支付宝/银行的脏格式吃得多深"。

## 2. 主对象：批次（batch）是一等公民

传统记账软件的主对象是**一笔账**；billkit 的主对象必须是**一次导入（一个批次）**。这一个差别决定整个信息架构。

一个批次的生命周期即产品骨架：

**接入 → 清洗/去重 → 分类 → 复核 → 导出 → 归档 → 增量**

落地要求：
- 每次运行产出一份 `build/batch.json` 清单：来源、文件哈希、参数、billkit 版本、条数与统计；
- 支持**幂等重跑**（同输入同参数结果一致）与**增量**（只处理新日期区间）；
- 支持**批次 diff**（这次比上次多了/少了/改了什么）；
- 面向极客，这是"可审计、可复现、可脚本串起来"的基础，不是装饰。

> 现状：`batch` 当前只是 AI 打标的 chunk size，尚未被当成一等公民；这是产品化第一个结构性动作。

## 3. 价值主线：把人工复核沉淀成资产

实测 6,533 条：自动 81.8%，接 AI 后待复核 **10.4%（约 680 条）**。**批量处理的价值天花板，由这套人工复核的边际成本决定**，不是由自动率决定。

三个动作：
1. 把人工从"逐行"压到"逐商户 / 逐规则"（现状已按对手方批量套用，继续做狠）；
2. 把每次人工判断**沉淀成可移植的知识库**（商户 → 分类、个人偏好），文件级、git 友好、可导出复用；
3. 让**下一批自动率单调上升**——这是唯一有复利的资产。

产品原则贯穿全程：**批量默认，单条例外。** 默认全自动，只把不确定的、金额异常的、新商户的挑出来让人看。

验收信号：连续两批导入，第二批自动率应高于第一批（因知识库继承）。

## 4. 护城河：解析适配器的广度 + 脏数据鲁棒性

不靠分类算法，靠"**多烂的账单都能吃进去**"。微信/支付宝/银行导出格式年年变，这是填不完但极高价值的地方。

工程对应：
- 每个来源一个**可插拔适配器** `src/adapters/<source>.py`（`detect()` 表头指纹 + `parse()`）；
- 每个适配器配一组**真实脱敏样本 + golden 回归测试**（格式一改，测试先红）；
- 分类后端（规则 / Ollama / OpenAI 兼容网关）当**可替换件**，随时换模型而不动管道。

## 5. 面向极客开源的具体主张

- **CLI-first、管道友好**：支持 `--in -` / `--out -`、`--json` 机器可读输出、稳定 exit code；
- **核心零第三方依赖**：可选 extras（`ai` 走 requests、`dev` 走 pytest），装得进任何环境；
- **契约优先**：`docs/03-reference/schema.md` 的输入输出字段就是合同，按语义化版本演进；
- **适配器 / 导出器插件化**：新增一个来源或出口，只需加一个文件 + 一组样本，社区可贡献；
- **golden-test 驱动**：所有格式差异靠测试固化，不靠人肉记忆；
- **许可证 MIT**（现状）。

衡量是否被采用（比 star 更实）：
- 他人 `pip install` 后能用真实账单跑通；
- 外部贡献的适配器数量；
- issue 里"新增来源/出口"请求的解决速度；
- 同一用户第二批的自动率提升。

## 6. 路线与验收

### P0 可交付 CLI
- `pyproject.toml` + 入口 `billkit`，`pip install .` 可用；
- 单测覆盖：分类规则、去重、导出映射、适配器解析；
- `--json` 输出与稳定 exit code。
- 验收：`billkit --help` 可用；`pytest` 绿；`billkit all` 对 `sample/` 产出三份导出且 beancount 0 错误。

### P1 批次一等公民 + 适配器插件化
- `batch.json` 清单、幂等重跑、增量、批次 diff；
- 适配器目录化，自动识别来源（表头指纹）。
- 验收：新增一个来源只需加 `adapters/<src>.py` + 一组 golden 样本。

### P2 知识库资产化（胜负手）
- 商户→分类知识库为可移植文件，复核界面写回；
- 每批记录自动率 / 复核率，趋势可见；
- 与账簿已有数据对账去重。
- 验收：连续两批、第二批自动率 > 第一批。

### P3 扩张
- 出口插件化（木木 / Firefly / beancount 之外可扩展）；
- 同一引擎换 schema，吃发票 / 银行流水 / 对账单等"非账单个人数据"（独立 profile）；
- 家庭 / 多人 profile。
- 验收：新增出口只需加 exporter + 映射测试。

## 7. 非目标（明确不做）

- 不做云同步 / 托管上传——保持纯本地、数据不出机；
- 不做移动端、不做保姆式手工记账；
- 不做银行 API 自动拉取（合规与维护成本高，交给用户导出文件）；
- 不为"非极客用户"承诺零配置——那是另一条产品线，会稀释本定位。

## 8. 关于商业化（诚实）

面向极客的开源产品，**清晰变现很难，也不该是首要目标**。首要目标是采用、声誉与可维护性。若要变现，现实路径是"开源核心 → 卖格式适配 / 托管导入 / 企业报销批量"这类服务，而不是订阅制。用户会为"一次省事"付一次性的钱，不会为"又一个记账工具"付月费。
